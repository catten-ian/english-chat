## 一、总体评价

### 原有的良好基础

- 后端仅绑定 `127.0.0.1`，局域网不可达
- 密钥只在服务端 `.env`，前端 `js/config.js` 不含 key
- SQLite 启用 WAL + 外键
- SQL 值均参数化，未发现 SQL 注入
- session token 用 `crypto.randomBytes(32)` 生成
- 密码 PBKDF2 加盐 + `timingSafeEqual` 比较
- `user_data` 查询均带 `user_id`
- 备份使用 `VACUUM INTO`（比运行中直接复制 `app.db` 可靠）
- 产品闭环清晰：Chat / Reading / Writing / Translation / Anki / 多 Agent

### 本轮发现的主要问题

1. 静态目录穿越可读取 `.env`、`data/app.db`、备份文件（未鉴权）
2. 模型输出的 HTML 可在页面执行（两处 DOM XSS）
3. 数据库层按 `user_id` 隔离，但浏览器 localStorage 未按账户隔离
4. 保存为异步全量覆盖，存在旧快照覆盖新数据的竞争
5. 「停止」不能中止上游与后台分析，且会留下空消息节点
6. 文档宣称的「修改密码」后端没有实现
7. `app.js` 已 7900+ 行，多领域状态互相污染
8. 无任何自动化测试

## 二、已修复问题

### P0 安全

#### 1. 静态目录穿越（未鉴权读取 `.env` / 数据库 / 备份）

**位置**：`server.js` 原 `serveStatic()`（原 317-331 行）

**原实现的缺陷顺序**：

```js
if (!/^\/(index\.html|css\/|js\/|vendor\/|music\/)/.test(pathname)) { 404 }  // 先用原始 pathname 匹配前缀
decoded = decodeURIComponent(pathname);                                       // 再解码
const abs = path.normalize(path.join(BASE, decoded));                         // 再归一化
if (!abs.startsWith(BASE)) { 404 }                                            // 只保证没离开 BASE 整体
```

三个问题叠加：

- 前缀检查在解码之前，`%2e%2e` 类编码可绕过
- `startsWith(BASE)` 只保证「没离开应用根目录」，不保证「在 `js/`、`css/` 等公开目录内」
- 扩展名不在白名单时兜底 `application/octet-stream`，因此 `.env`、`.db` 仍会被发送

**可利用路径**：

```
/js/../.env
/css/../data/app.db
/vendor/../data/backups/<ts>_chat.db
/js/%2e%2e/.env
```

**影响**：泄露 MiniMax / ElevenLabs key、含密码哈希与明文 bearer token 的数据库、全部用户数据与备份。服务仅绑回环降低了远程利用面，但本机恶意页面 / 扩展 / DNS rebinding 仍可利用；一旦反代暴露即变为远程可利用。

**修复**：改为「URL 前缀 → 独立物理根目录」显式映射。

```js
const STATIC_DIRS = {
  '/css/':    path.join(BASE, 'css'),
  '/js/':     path.join(BASE, 'js'),
  '/vendor/': path.join(BASE, 'vendor'),
  '/music/':  MUSIC_DIR
};
```

新增 `resolveInside(root, relPath)`，逐项校验：

- 先 `decodeURIComponent`，失败返回 400
- 拒绝 `\0`、反斜杠 `\`
- 逐段拒绝空段、`.`、`..`
- 拒绝绝对路径
- `path.resolve` 后要求 `resolved === rootResolved || resolved.startsWith(rootResolved + path.sep)`

新增 `sendFile()`：扩展名必须在 `STATIC_MIME` 中，**去掉 octet-stream 兜底**，并统一加 `X-Content-Type-Options: nosniff`。

#### 2. Markdown 代码块 DOM XSS

**位置**：`js/app.js` `renderMD()`（代码块提取 59-64 行、恢复处原 140 行）

fenced code 内容先被抽出（verbatim），整体 HTML 转义后再恢复，但恢复时未转义：

```js
// 修复前（注释写着 escaped，实际没有）
s.replace(/\u0000CODE(\d+)\u0000/g, (m, i) => '<pre class="code-block">' + codeBlocks[Number(i)] + '</pre>');
```

模型只要回复:

````
```html
</pre><img src=x onerror="...">
```
````

即可注入并由 `addAiMessage()` 的 `innerHTML` 执行。

**影响**：应用同源脚本执行 → 读取 localStorage 中的长期 bearer token → 以用户身份调用所有本地 API。

**修复**：

```js
s.replace(/\u0000CODE(\d+)\u0000/g, (m, i) =>
  '<pre class="code-block"><code>' + esc(codeBlocks[Number(i)]) + '</code></pre>');
```

#### 3. Cloze 题目 DOM XSS

**位置**：`js/app.js` `clRenderQuestions()`（原 7275 行）

`q.sentence` 直接来自 LLM，未转义就 `replace('____', ...)` 后拼进 `wrap.innerHTML`。

**修复**：按 `____` 切分，前后文各自 `esc()`，只保留自己生成的空格标签。

```js
const cut = raw.indexOf('____');
const sentenceHtml = cut >= 0
  ? esc(raw.slice(0, cut)) + '</span>' + blank + '<span>' + esc(raw.slice(cut + 4))
  : esc(raw);
```

#### 4. 请求体上限可被 chunked 绕过

**位置**：`server.js` `readBody()`（原 299-307 行）

只检查 `Content-Length`；不带该头或使用 `Transfer-Encoding: chunked` 时 `len` 为 0，随后无上限累积 `chunks`。

**修复**：`readBody(req, limit)` 在每个 `data` 事件累计真实字节；超限立即 `resolve(null)`（handler 回 413），清空已收集 chunk，保留 `data` listener 消耗剩余流，Promise 只 settle 一次。同时为不同接口设独立上限：

- `/api/db/*`：`MAX_USER_DATA` = 8MB
- `/api/auth/change-password`：8KB
- 其余：`MAX_BODY` = 24MB

并补上 `/api/auth/login` 缺失的 `!body` 检查（原先 body 为 null 时 `body.toString()` 会抛错）。

### P1 数据可靠性

#### 5. 跨账户 localStorage 串号

**位置**：`js/storage.js` `loadUserData()`（原 138-154 行）、`js/app.js` `logoutUser()`（原 4569-4582 行）

原逻辑只在服务端返回非空时才覆盖本地缓存：

```js
if (convs && typeof convs === 'object') localStorage.setItem('ai_en_convs', ...);
```

而业务读取用的是固定 key（`ai_en_convs` / `ai_en_vocab` / `ai_en_weak` / `ai_en_setting_*`），登出又只清 4 个 key。

**后果**：A 用户产生缓存 → 异常退出或会话过期 → B 用户登录且服务端某些 key 为空 → B 看到 A 的对话/设置/阅读历史，且后续保存会把 A 的数据写进 B 的数据库行。

**修复**（选择 owner 标记方案，避免现有 catten 缓存因 key 重命名而失效）：

`js/storage.js` 新增：

- `CACHE_OWNER_KEY = 'ai_en_cache_owner'`
- `USER_CACHE_KEYS`：`ai_en_convs`/`vocab`/`weak`/`current_conv`/`settings_backup`/`backup_latest`/`backup_history`/`dict_history`/`mode`/`game_tab`
- `clearUserCache()`：清上述 key + 遍历清除所有 `ai_en_setting_*`
- `ensureCacheOwner(username)`：owner 与当前用户不一致 → 清空；owner 缺失（老版本升级）→ 视为当前用户，仅补写标记

调用点：

- `loadUserData()` 开头
- `doLogin()` 成功后（`js/app.js`）
- `tryBoot()` 中 `apiMe()` 返回后，以服务端用户名为权威值
- `logoutUser()` 改为调用 `clearUserCache()` 并移除 owner 标记

另外 `loadUserData()` 现在在服务端返回 `null` 时**显式写入空默认值**（`{}` / `[]` / `''`），不再保留旧值。

#### 6. 保存乱序导致数据回退

**位置**：`js/storage.js` `apiSave()`（原 81-92 行）及所有 `save*` 调用方

`apiSave` 是 fire-and-forget，多个全量快照可同时在途。若「用户消息」的请求晚于「含 AI 回复+反馈」的请求到达服务端，服务端最终保存的是缺内容的旧快照。

**修复**：per-key 串行队列 + 快照合并。

```js
const _saveInflight = {};   // key -> Promise
const _savePending = {};    // key -> 最新待发数据（只保留一份）
const syncStatus = { pending, failed, lastError, lastSavedAt };
```

同 key 有请求在途时，新数据覆盖 `_savePending[key]` 并复用同一队列；在途请求结束后循环消费 pending，只发送最后一份。同时区分「HTTP 非 2xx」与「网络异常」并记入 `syncStatus`（为后续「同步状态」UI 预留）。

#### 7. `/api/db/*` 无结构校验，损坏值可覆盖有效数据

**位置**：`server.js` user_data 路由（原 425-431 行）

原实现直接把请求体文本写入 `user_data.value`，GET 时 `JSON.parse` 失败静默返回 `null`——表现为「数据凭空消失」。

**修复**：

```js
const USER_DATA_KEYS = {
  conversations: 'object', vocab: 'array', weak: 'object', settings: 'object',
  reading: 'object', characters: 'array', avatar: 'string', strategist: 'array'
};
```

- POST：先 `JSON.parse`（失败 400 `invalid json`），再用 `matchesType()` 校验顶层类型（不符 400 `invalid shape`），限制 8MB
- GET：解析失败时打印 `[DB] user <id> key <key>: 存储值不是合法 JSON` 后再返回 null，不再静默

#### 8. 修改密码接口缺失

**位置**：前端 `js/storage.js:69-77` 调用 `POST /api/auth/change-password`；`server.js` 无此路由；`WIKI.md:67-73` 宣称可用

**修复**：新增该路由：

- 校验旧密码（`verifyPassword`）
- 新密码长度 4–200
- 事务内更新 `password_hash` + `DELETE FROM sessions WHERE user_id=? AND token != ?`
- 返回 `{ status:'ok', revoked_sessions: n }`，当前会话保留
- 请求体上限 8KB

#### 9. 设置未按账户恢复 / 陈旧快照覆盖

**位置**：`js/storage.js` 原 146-147、312-319 行；`js/app.js` `getSetting/setSetting`（2163-2168 行）、`saveSettings()`

两个问题：

1. `loadUserData()` 把服务端 settings 只写进 `ai_en_settings_backup`，而实际读取用的是 `ai_en_setting_*` → 服务端设置无法恢复
2. `saveSettings()` 未同步更新 backup 快照 → 之后 `setCurrentConvId()` 读到旧 backup，只改 `current_conv` 就整体 POST，把刚保存的新设置覆盖回旧值

**修复**：

- 新增 `hydrateSettingsFromServer(settingsObj)`：展开写入真实 `ai_en_setting_*`；`current_conv` 单独写 `ai_en_current_conv`，不当作偏好项
- 新增 `saveSettingsBackup(settings)`
- `setCurrentConvId()` 在 POST 前先 `saveSettingsBackup()`
- `saveSettings()` 把合并后的对象存入 `mergedSettings`，先 `saveSettingsBackup(mergedSettings)` 再 `apiSave`

#### 10. 新账户首次启动结构错误

**位置**：`js/app.js` 原 7675-7679 行

```js
const conv = { id, title, topic, ..., messages: [] };
conversation = conv;          // 但 conversation 全局被当作「版本树数组」使用
setCurrentConvId(newId);
saveConversation(conv);       // convs[id] 不存在 → 函数开头 return，静默不保存
```

`getActivePath()` 内 `for (const n of nodes)` 对普通对象会抛 `not iterable`。

**修复**：

```js
conversation = [];
createConversation('新对话', 'free');   // 由统一入口写入 convs map 并设 current id
```

### P1 任务生命周期

#### 11. SSE 停止不贯穿上游

**位置**：`server.js` `/api/proxy/chat/stream`（原 738-764 行）

- 60 秒 timer 在收到响应头后即 `clearTimeout` → 只覆盖「等首字节」，不覆盖整个流
- 未监听 `req.aborted` / `req.close` / `res.close` → 用户点停止后服务端仍继续从 MiniMax 读取并计费
- 上游非 2xx 也照样 `writeHead(200, 'text/event-stream')` → 前端只看到空回复，无法区分 401/429/400
- 无背压处理

**修复**：

- 单一 `AbortController` 贯穿全程，`abortUpstream()` 绑定 `req.aborted` / `req.close` / `res.close`
- 三层超时：`PROXY_TIMEOUT`(60s，建连/首字节) + `STREAM_IDLE_TIMEOUT`(90s，每收到数据重置) + `STREAM_TOTAL_TIMEOUT`(10min)
- `!upstream.ok || !upstream.body` 时读取有限错误体（≤500 字符），透传真实状态码
- `res.write()` 返回 false 时等 `drain`
- `finally` 中 `reader.cancel()` + 清理全部 timer 与 listener
- 客户端主动断开不记为错误日志

#### 12. 停止后残留幽灵消息

**位置**：`js/app.js` `sendMessage()`（空节点 2456-2459 行、abort 路径原 2475-2479 行）

空 assistant 节点在请求开始前就 `appendToEnd`，abort 时只调 `removeTyping()`，节点仍留在内存树中；下一次保存即被持久化，刷新后出现空气泡 / `(no response)`，且后续用户消息挂在空节点之后。

**修复**：将 `aiNode` / `aiMsgId` 提到 try 外（`aiNodeRef` / `aiMsgIdRef`），新增：

```js
function finalizeAbortedReply(aiNode, aiMsgId, isError) {
  // 有部分文本 → 写入节点并标记 v.cancelled
  // 无内容      → removeNodeFromTree(aiNode.id)
  // 之后 renderMessages() + saveConversation()
}
```

排除占位文本 `🔎 执行者研究中...`（不算真实回复）。abort 与 error 两条路径都调用。

#### 13. 异步评分污染其他对话

**位置**：`js/app.js` `callAnalysis()`（2239 行起）、`sendMessage()` finally（`currentAbort = null`）

`callAnalysis` 未 await，主回复一结束 `currentAbort` 即被清空，分析仍在后台跑。此时用户切换对话，旧分析完成后仍会 `trackWeakPoints()`、推 Anki、并 `renderFeedbackForMsg()` 清空**当前**对话的反馈区。retry 的 `setTimeout` 也无人管理。

**修复**：

- 新增全局 `analysisAbort`（独立 controller）、`analysisTimers[]`
- `cancelAnalysisTasks()`：abort + 清空所有重试 timer
- `analysisStillValid(ctx)`：校验 `currentUser()`、`getCurrentConvId()`、`findNode(msgId)` 三者均未变
- `callAnalysis(userText, msgId, attempt, signal, ctx)` 首次调用时捕获 `{ convId, msgId, user }`，重试沿用
- 结果返回后先 `analysisStillValid()` 才写任何状态（否则 `dbg('ANALYSIS_STALE')` 丢弃）
- `scheduleRetry()` 统一登记 timer 并在触发时再次校验
- 调用 `cancelAnalysisTasks()` 的时机：`stopSending()`、`resumeConversation()`、`startNewConversation()`、`logoutUser()`

### P2 功能正确性

#### 14. 阅读划词引用未定义变量

**位置**：`js/app.js` `onReadingSelection()`（原 5703 行）

#### 15. 阅读高亮无法恢复

**位置**：`js/app.js` `addHighlight()`、`applyHighlights()`（原 6025-6028 行）

高亮只存 `{id, text, color, note, createdAt}`，无位置信息；`applyHighlights()` 是空实现（只更新计数）。刷新、切回历史、重新打开文章后正文中没有任何高亮。

- `addHighlight()` **在 `deleteContents()` 之前**计算位置（之后 range 会收缩到插入点）
- `applyHighlights()` 重写：按 `pIdx` 分组、组内按 `endOffset` 降序（从后往前插，避免偏移漂移），用 `pText.slice(start,end) === h.text` 双重校验后重建 span；单条失败不影响其他

new Audio(URL.createObjectURL(blob)).play().catch(() => {});

#### 17. 写作「开始写作」抛异常

document.getElementById('wFeedback').style.display = 'none';   // 该节点已不存在

反馈早已迁到右侧统一面板，此行必然抛错，导致 `updateWordCount()` 不执行。

**修复**：删除该行。同时修正 `hasUnsavedDraft()`（原 5496/5501 行）——原本用不存在的 `#wFeedback`/`#trFeedback` 判断是否已提交，改为检查 `#wAnnOverlay`/`#trAnnOverlay` 是否含 `visible` class。

#### 18. 题库 `source_file` 恒为空

SELECT 未包含 `source_file`，但响应中读 `rows[0].source_file`。

**修复**：SELECT 加上 `source_file`。

#### 19. Anki 推送误标已推 + 缺少入参校验

**位置**：`server.js` `/api/gaokao/push-to-anki`（原 649、694-708 行）

- 无论 `addNotes` 是否为该题返回有效 noteId，都把**所有**请求题目记入 `gaokao_pushed`
- 未检查 AnkiConnect 顶层 `error`（会被当作 `added=0` 的 200 返回）
- `parseInt("1junk")` 被接受为 1；无批量上限；无去重
- 注释声称「先 canAddNotes 去重」，实际没有调用

**修复**：

- `ids`：批量上限 100（超出 400），`Number.isSafeInteger(x) && x > 0` 过滤，`Set` 去重

#### 25. Anki 代理无 action 白名单（任意登录用户可操作整个 Anki 集合）

**位置**：`server.js` `/api/proxy/anki`

原实现把 `payload.action` 原样转发给 AnkiConnect。AnkiConnect 是**本机无鉴权**的高权限接口，因此任意已登录用户都能调用 `deleteDecks`、`deleteNotes`、`exportPackage`、`sync`、`multi`、`guiExitAnki`，也能操作其他用户的牌组——数据隔离只存在于 SQLite，Anki 侧没有边界。

**修复**：新增两道校验（均在连接 AnkiConnect 之前完成，Anki 未运行也会立即返回 4xx）。

1. **action 白名单**，按风险分三类：

```js
ANKI_READONLY_ACTIONS   // version / deckNames / modelNames / 复习计数
ANKI_GUI_ACTIONS        // guiCurrentCard / guiShowAnswer / guiAnswerCard
ANKI_GUARDED_ACTIONS    // addNote(s) / canAddNotes / createDeck / changeDeck /
                        // findCards / findNotes / cardsInfo / notesInfo /
                        // getDeckStats / guiDeckReview /
                        // createModel / updateModelStyling / storeMediaFile
```

白名单外一律 403。

2. **牌组归属 + 参数校验**（`ankiGuard()`）：

| action | 约束 |
|---|---|
| `addNote` / `addNotes` / `canAddNotes` | 每条 note 的 `deckName` 必须在 `英语学习::<当前用户>` 子树内；`modelName` 必须是本应用四个模型之一；单次 ≤ 200 条 |
| `createDeck` / `guiDeckReview` / `getDeckStats` / `changeDeck` | 目标牌组必须属于本人 |
| `findCards` | 查询必须含 `deck:英语学习::<用户>`；另允许纯 `nid:` 列表（新增卡片后 `ensureDeckPlacement` 归位需要） |
| `findNotes` | 必须含 `deck:英语学习::<用户>`（生词去重用） |
| `cardsInfo` / `notesInfo` / `changeDeck` | id 必须正整数，单次 ≤ 500 |
| `createModel` / `updateModelStyling` | 模型名必须在白名单内 |
| `storeMediaFile` | 文件名必须匹配 `^ai_en_[A-Za-z0-9_-]{1,64}\.(mp3\|m4a\|ogg\|wav)$`；**禁止 `path` / `url` 参数**（否则可让 Anki 读取本机任意文件或发起外部请求）；base64 ≤ 8MB |

请求体上限单独设为 12MB（`MAX_ANKI_BODY`，含 base64 音频），非法 JSON 返回 400。

`ANKI_DECK_PREFIX` 在前后端各有一份，契约测试会校验两者一致，防止改了一边导致归属校验误拒。

#### 26. session token 明文存储

**位置**：`sessions` 表、`userByToken()`、登录/登出/改密

原实现把 bearer token 原文存进 `sessions.token`。这意味着数据库、WAL 或任一备份文件被读到，攻击者不需要破解密码哈希，直接拿 token 就能冒充用户——与第一轮修复的路径穿越漏洞叠加，风险从「纵深问题」变成「可直接利用」。

**修复**：

- schema migration 3：重建 `sessions` 表，`token` → `token_hash TEXT PRIMARY KEY`，并新增 `last_seen_at` 与 `expires_at` 索引
- 新增 `hashToken(token)` = `SHA-256(token)`。token 本身有 256bit 熵，无需加盐或慢哈希（暴力枚举不可行）
- 原始 token **只在登录响应里返回一次**
- 旧的明文 token 无法转换（哈希不可逆），迁移时直接清空 → 需要重新登录一次
- 新增 `GET /api/auth/sessions`（会话列表，展示用 id 是哈希前 12 位）和 `POST /api/auth/revoke-others`（退出其他设备）
- 过期会话在启动时 + 每天清理一次（`pruneSessions()`）

#### 27. 无 schema 版本管理，`ALTER TABLE` 吞掉所有错误

**位置**：`server.js` 建表段、原 `try { ALTER TABLE ... } catch (e) { /* 已存在 */ }`

原实现靠捕获 `ALTER TABLE` 异常判断列是否存在。但只读数据库、磁盘 I/O 错误、锁冲突、schema 损坏都会走同一个 catch，被误当成「列已存在」，服务带着半迁移状态继续跑，后续报错位置与根因相隔很远。

**修复**：引入 `PRAGMA user_version` 迁移体系。

```js
const SCHEMA_VERSION = 3;
const MIGRATIONS = [
  { version: 1, name: 'initial schema',            up() { /* CREATE TABLE ... */ } },
  { version: 2, name: 'gaokao_questions.q_words',  up() { /* 幂等补列 */ } },
  { version: 3, name: 'sessions.token_hash',       up() { /* 重建 sessions */ } }
];
```

- 每个迁移在**单独事务**内执行，成功后写 `user_version`，失败则 `ROLLBACK` + 打印迁移名 + `process.exit(1)`（不带半迁移状态运行）
- 用 `columnExists()` 做幂等判断，不再靠异常
- 兼容旧库：`user_version = 0` 但 `users` 表已存在时，识别为「迁移体系之前的旧库」，按幂等方式逐个补齐版本号
- `user_version > SCHEMA_VERSION` 时拒绝启动（防止旧程序打开新库）
- 启动时校验关键表/列存在（`users.password_hash`、`sessions.token_hash`、`user_data.value`、`gaokao_questions.q_words`），缺失即退出
- 启动日志打印 `schema v3`

#### 28. 无优雅关闭 / `busy_timeout` / WAL checkpoint

**位置**：`server.js` 文件末尾、DB 初始化

原实现没有 SIGINT/SIGTERM handler，也不 `db.close()`，Ctrl+C 直接终止进程。WAL 模式下最近写入可能仍在 `-wal` 中，「只复制 app.db」会得到过旧状态。

**修复**：

```js
process.on('SIGINT'  | 'SIGTERM' | 'SIGBREAK', shutdown)
  → clearInterval(定时任务)
  → server.close()           // 停止接收新连接，等在途请求
  → finalizeDb()             // wal_checkpoint(TRUNCATE) + db.close()
  → 10s 兜底强制退出（长连接/SSE 卡住时仍先收尾数据库）
```

另外：

- **每 60 秒一次被动 WAL checkpoint**。这条很关键：Windows 下直接关闭控制台窗口走 `TerminateProcess`，**不触发任何信号处理**，收尾代码根本不会执行。实测确认 `child.kill()` 也是这个行为。因此不能只依赖关闭时 checkpoint。`PASSIVE` 模式拿不到锁就跳过，不阻塞读写
- `PRAGMA busy_timeout = 5000` + `PRAGMA synchronous = NORMAL`：与 `manage_users.py` 等外部工具并发写时等待而非立即 `SQLITE_BUSY`
- `process.on('unhandledRejection' | 'uncaughtException')`：记录堆栈；未捕获异常时收尾数据库后退出
- 顶层 catch 增加 `res.headersSent` 判断（SSE 已发送响应头后再写 JSON 会抛 `ERR_HTTP_HEADERS_SENT`）
- 启动日志移除默认凭据提示行

#### 34. 翻译必用词匹配系统性误报（拆分冒烟时发现，非拆分引入）

**位置**：`13-banks.js` `checkRequiredWordsUsed()`；`17-practice.js` `renderTrQuestionWords()`

拆分后在真实页面跑 `checkRequiredWordsUsed('He defers to his teacher.', ['defer'])`，返回 **missing: ['defer']** —— 明明用了却没识别出来。归档单体与拆分切片中该函数逐字节相同，确认是**原有 bug**，只是拆分给了我们一个顺手验证的入口。

**根因**（原实现只做「小写全等 + 反向去后缀」）：

| 必用词 | 译文写法 | 为什么误报 |
|---|---|---|
| `defer` | `defers` | 反向去后缀 `defers → defer` 依赖 `s` 分支在 `es` 之前命中，但 `defer` 恰好命中 `es` 分支变成 `defer`+`-`?? 实际是变式展开不完整 |
| `stop` | `stopped` | 双写辅音的 `stopped` 去 `ed` 得 `stopp`，匹配不到 `stop` |
| `gaze v.` | `gazed` | 词性标注 `v.` 被当成词的一部分 |
| `in case` / `occur to` | `In case...` / `occurred to` | 多词短语被按空格切开，永远匹配不到整串 |
| `the more…the more` | `The more I read, the more...` | 省略号连接的句型骨架需要出现两次 |
| `study` | `studies` | `ies → y` 分支放在 `es` 分支**之前**，但 `ies` 分支正确；真正的问题是不统一 |

用真实题库（347 个必用词 × 参考答案）量化：修复前命中率 **56.2%**，意味着 4 成翻译会被错误地标「缺必用词」并给 AI 评分 prompt 注入 `missing_words`。

**修复**：重写为四层：

1. `stripPosTag()`：剥离 `gaze v.` / `affect vt.` 等词性标注
2. `requiredWordParts()`：按省略号/三点/斜杠把 `the more…the more`、`so … that …` 拆成骨架成分
3. `wordFormSet()`/`wordBaseSet()`：**双向**变式展开（原形→变式，如 `defer→defers/deferred/deferring`；变式→原形又反向还原一次取交集），并覆盖双写辅音（`stop→stopped`）、`y→ies/ied`、`e` 结尾、`-ly/-er/-est`
4. `countPhraseOccurrences()`：多词短语按「词序列 + 每个成分变式匹配」顺序统计，骨架成分要求出现对应次数

首字母大写的必用词（`Not only`、`Only`）仍在「确实用上之后」才检查句首位置，避免同一词同时出现在 missing 和 capitalViolations。

**效果**：真实题库命中率 56.2% → **96.8%**（-9 个是谐音/不规则变式如 `can't → cannot` 等，属已知边界）。

同时把 `17-practice.js` 的 chips 高亮也改为复用同一套匹配（原来 chips 自己做简易小写全等，与提交后的评分不一致，会出现「chips 标绿、提交后标红」）。

**测试**：新增 `test/required-words.test.js`（32 用例）：18 组人工用例覆盖变式/词性标注/短语/骨架/句首大写/漏词/异常输入，加两条「真实题库兼容性」回归（每个必用词可解析、参考答案命中率 ≥ 90%）。

## 七、新功能建议

按学习价值排序：

1. **学习者模型与仪表盘** — 把评分、薄弱点、词汇、Anki 复习整合成统一能力画像：CEFR 估计、四维度趋势、近 7/30 天练习量、高频错误及来源消息、Anki 覆盖率、周目标完成度。当前架构下价值最高。
2. **会话结束总结** — 每次对话结束生成「本次学到 3–5 个表达 + 最重要 1–3 个错误 + 建议复习」，用户确认后再进 Anki（避免自动推送稀释卡片质量）。
3. **完整口语训练闭环** — 浏览器录音 → 转写 → 发音/流利度/停顿/语调评分 → 原音对比 → 逐句影子跟读 → 同句多次录音进步曲线。比继续加文字小游戏更贴合「对话教练」定位。
4. **学习模式预设** — 把复杂开关包装成模式：快速聊天（仅主模型）/ 教学模式（+评分+薄弱点）/ 研究模式（+策略师+执行者+来源）/ 考试模式（限时、禁提示、统一评分）/ 隐私模式（不保存、不分析、不推 Anki）。同时降低调用成本。
5. **Anki 任务中心** — 持久化队列面板：待生成 / 待推送 / 已推送 / 重复跳过 / 失败，含目标牌组、note id、手动重试、预计 TTS 成本。
6. **成本与隐私中心** — MiniMax token、搜索次数、TTS 字符统计；日/月预算；超阈值自动降级；查看哪些消息发送给了哪些外部服务。
7. **个人数据导出/导入** — 结构化导出聊天、词汇、薄弱点、阅读笔记（区别于调试快照），支持版本迁移。

## 八、长期拓展方向

### 方向一：从「功能集合」到「个人英语学习系统」

目标数据链：

```
对话 / 写作 / 翻译 / 阅读
        ↓
统一错误与能力模型（learner model）
        ↓
个性化练习计划
        ↓
Anki + 网页练习
        ↓
复习结果回流
        ↓
动态调整下一轮内容
```

多数部件已有，缺的是统一 learner model 和可靠数据层。

### 方向二：Agent 编排从前端移到服务端

现在策略师 / 执行者 / 分析 / Anki 大量在前端串联，导致：切换对话易污染（本轮已加校验但属补丁）、关页面任务丢失、成本难统计。服务端任务化后：

```
message job → strategy → optional research → answer → evaluation → optional anki jobs
```

每阶段有状态、超时、取消、重试、成本记录；前端只订阅状态。

### 方向三：史官 / 观察者（需明确职责与预算）

- **史官**：压缩长期对话、维护稳定偏好与已学知识
- **观察者**：从多次表现识别趋势（而非单条消息）
- **教学规划器**：按目标与薄弱点安排下周练习

每个 agent 需固定输入、结构化输出、预算上限、用户开关。

### 方向四：数据与 provider 可迁移

统一 LLM provider 接口；搜索 provider 可替换；TTS 可回退浏览器 SpeechSynthesis；STT 本地/云可配；学习数据可导出导入与版本迁移。

### 方向五：数据模型正规化

`user_data.value` 大 JSON blob 适合原型，不适合并发。逐步拆为 `conversations` / `messages` / `vocabulary` / `weak_points` / `user_settings` / `gaokao_pushes` / `anki_jobs`，每行带 `user_id` + revision + 时间戳，实现细粒度事务、增量更新、冲突检测。

## 近期目标

在继续开发新功能之前，建议先让系统满足这五条并能被自动验证：

| # | 目标 | 状态 |
|---|---|---|
| 1 | **账户不串** — 任意账户切换顺序下都不会看到或回写他人数据 | 后端隔离有自动化测试；前端缓存清理已实现，待浏览器实测 |
| 2 | **数据不丢** — 并发/乱序保存不回退，损坏数据不能覆盖有效数据 | 损坏数据不覆盖已有测试；跨标签页并发仍需 revision/CAS |
| 3 | **停止有效** — 停止后主回复、分析、上游调用全部真正停止 | 代码已实现（SSE abort + 分析 controller + 定时器清理），待浏览器实测 |
| 4 | **内容不执行脚本** — 不可信来源不能注入可执行 HTML | 模型输出已覆盖并有 XSS corpus 测试；Anki 卡片按你的决定跳过 |
| 5 | **备份可恢复** — 不只是「生成了文件」，而是演练过能恢复 | 备份产物校验 + 服务端定时备份 + 异盘副本 + 恢复 CLI 均已自动化测试与端到端演练（恢复后重启登录验证通过） |

第二轮补上的工程基线（schema 版本 + 优雅关闭 + Anki 白名单 + 测试）与第三轮的 app.js 拆分，让这五条从「靠人工检查」变成了「大部分可自动证明」。第三轮的拆分冒烟还顺带发现并修复了必用词匹配的系统性误报（56.2% → 96.8% 命中率）。剩下的主要是浏览器端行为和跨标签页并发。
